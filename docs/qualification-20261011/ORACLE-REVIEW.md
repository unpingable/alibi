## Disagreements and distinctions

The route-mask result is stronger than a malformed-input concern: it is a legal-shaped non-default route that violates the collector's named interpretation. It should not be dismissed as unsupported data. Conversely, do not label every parser helper's result an observed false CLEAR; that requires a verdict observation or a plainly marked inference.

The arbitrary-text log finding needs two separate statements. The local oracle establishes that this particular command output is not observed host evidence. The byte string itself does not establish that: kernel message bodies can be arbitrary text, and a substituted command could imitate any textual timestamp. The timestamped healthy fixture proves only a positive formatting control, not that genuine kernel logs satisfy a proposed new parser. Source-format validation is worthwhile but cannot prove command provenance or the absence of earlier lost messages. A universal malformed-log-detection claim would exceed any proposed regular-expression repair.

The timeout counterexample is independently convincing because elapsed time exceeded the nominal budget by about 900 ms while the child status was success. Scheduler overhead alone is not a credible explanation for the exact retained-pipe lifetime. It does not establish useful progress, clean descendant retirement, or a global process/resource bound. A repair that abandons reader threads can bound one return while accumulating threads and buffers across many mounts; review that separately. A repair that kills only the direct child does not establish EOF on inherited pipes. A descendant/process-group policy must stay within the child execution authority boundary.

The df identity issue remains distinct from range checks. Comparing a returned textual device name to an earlier mount string can reject some substitutions but does not prove the same mounted object or generation; aliases and legitimate path formatting also complicate that comparison. An actual mount-transition experiment with independent mount identity is still required. No repair should claim temporal filesystem consistency merely from rejecting `(100,101)`.

## Log truncation and completeness

Known truncation cannot be recorded as complete negative evidence for the original requested log window. This includes an explicit byte cap, read error after a prefix, missing final fragment known to be part of a record, or transport failure. Retained positive records may still justify D; an incomplete required log without a positive yields U. If the command collector returns only `Err` on truncation it can avoid false CLEAR but may lose a positive: document that limitation instead of claiming retained-positive semantics.

A full successful read of the **currently retained** dmesg output may be called acquisition-complete within that explicitly bounded retained-log envelope. It cannot establish complete since-boot history, continuous retention, freshness of all records, or absence of events that were overwritten before collection. Baseline design already discloses ring wrap; do not reclassify that disclosure as a new universal since-boot guarantee. Record any known loss. If the desired conclusion depends on an unavailable earlier interval, U is required for that expanded claim. A format prefix and exit-zero command do not resolve this distinction.

A deliberately bounded log prefix is a narrower observation, but silently redefining the existing required evidence window to the captured prefix after hitting a cap would manufacture completeness. Any intentional source-window redesign needs an explicit contract decision, not a parser workaround. Receipt V2 can retain a partial/none status and detail without silently changing its schema.
